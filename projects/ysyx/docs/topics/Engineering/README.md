# Engineering：工程文档

对 ysyx-workbench（含其配套运行环境）所做的改造的工程文档。体例沿用 `Embedded-linux/Engineering/` 与 `Loongarch_NPU_SoC/Engineering/` 的既有写法。

和 `Knowledge/` 的关系：`Knowledge/` 是教材，读者是正在学这门课的人，按讲义阶段推进；本目录是工程文档，读者是要接手改造工程的人，按代码结构和开发时间线推进。同一件事在两边都出现是正常的，落点不同：教程讲"这个知识点怎么学会"，这里讲"这段代码为什么长这样、这一行在算什么"。

## 目录

| 目录 | 收录范围 | 维护方式 |
| --- | --- | --- |
| [Todo/](Todo/) | 学习与项目的总路线；不再按工作点分文件 | 工作点完成后进 TechReports；总路线长期存在 |
| [Bugs/](Bugs/) | 未修复的在产缺陷 | 一个缺陷一个文件；修复后删除文件，内容并入 TechReports |
| [TechReports/](TechReports/) | 每个工作点的开发过程 | 一层一个系列，完成一个工作点增加一章，写完定稿 |

## 流转规则

1. 开工前在 `Todo/学习与项目路线.md` 对应阶段里写清要解决什么、判据是什么。
2. 过程中的实测数字回填到路线文件的阶段表，不另开 Todo。
3. 过程中出现修不掉的缺陷，在 `Bugs/` 另开一条，注明现有判据为什么没覆盖到它。
4. 工作点完成且判据全绿之后，在 `TechReports/` 对应系列增加一章，并回路线勾状态。

## 项目规则：提交即更新文档

**每一次 commit，都要在同一次 commit 里把它影响到的文档改完。** 文档滞后于代码，等价于文档不存在。

| 改动 | 必须同步的文档 |
| --- | --- |
| 完成一个工作点（一个 PA 部分完成、一条流水线级打通、一次架构改造） | `TechReports/` 增加一章，并在 `Todo/学习与项目路线.md` 里勾状态 |
| 讲义阶段推进（学完一个部分、一组实验全绿） | 项目 README 的当前进度节 + `Knowledge/tutorials/` 对应篇 + 路线勾状态 |
| 发现一个改不掉的缺陷 | `Bugs/` 新增一条，写明现有判据为什么没覆盖到 |
| 某章教程完成 | 仓库对应 README/路线的状态栏 |
| 教程或报告引用的路径、文件名、章节号变化 | 引用方就地订正，不留死链 |

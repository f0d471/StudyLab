# Bugs：未修复的在产缺陷

一个缺陷一个文件，命名 `NN-一句话病名.md`。修复后删除文件，内容并入 TechReports 对应章。体例继承自 raw 旧仓 `note/bug/00-缺陷档案规范.md`（原 abstract-machine 复盘沉淀，全文可在旧仓查阅），核心规则收编如下。

## 档案是纪实，不是题库

不设"你先自己找找看"的关卡，不藏答案；但也不是流水账。一份合格的档案同时交付三样东西：**当时发生了什么、背后的知识是什么、为什么改成了这样而不是那样**。

```text
卷首表      文件、函数、缺陷类型、严重度、引入于哪个 commit、什么时候怎么发现的
一、这东西本该干什么   背景知识：函数的来历、名字怎么拼出来的、标准怎么规定的
二、现场               当时看到的现象，加最小复现代码
三、追查               怎么从现象走到病灶的，包括走过的弯路
四、病理               为什么会写成这样，为什么难查
五、改动               改了什么，以及为什么不用别的改法
六、留下什么           可迁移的模式，加本次刻意没处理的遗留
```

第一节必须有：不知道正确行为，就不可能识别错误行为。前置知识各篇不重复，谁先出现写在谁那里，后面的引过去。第三节要写真实的追查过程包括判断错的方向；第五节要写清被否决的方案。

**一条铁律：没有最小复现的"我觉得这里不对"，不算发现缺陷。** 复现代码要能直接粘进测试文件跑起来。

## 通用缺陷模式（按"下次还会犯"排序）

一周目 abstract-machine 复盘沉淀，本工程复用；新的模式随新档案追加。

1. **同一个不变量被手写多遍，只维护了其中一处**。根治是把不变量收进单一抽象，不靠自觉。
2. **用一个正常运行中会自然出现的值当哨兵**。两个独立的是非题就该有两个变量。
3. **`size_t` 参与减法前没证明被减数够大**。无符号回绕编译器不警告，要 `-Wextra`。
4. **状态机在循环体内多次前进，却只在入口检查了终止条件**。写解析器要数清楚每个 `p++` 前能否保证 `*p != '\0'`。
5. **「能跑通」被当成了提交标准**。调试残留不会导致失败，只能靠提交前逐行看 diff 或带开关的宏。
6. **继承来的代码 ≠ 验证过的代码**。上游骨架是"够用就行"的简化实现，且不写明简化了什么。
7. **简化可以，但必须写在注释里**。不写明简化了什么，取舍就退化成缺陷。
8. **同一个知识有第二份实现，就一定会漂移**。发现要写 `#ifdef` 时，先找有没有现成抽象。
9. **批量修改必须有"预期不变的集合"，事后机械验证**。防线是剥掉注释后与 HEAD 逐字比对的机械检查，不是"我改的是注释"这个意图。

## 方法论：先证明你的测试能报错

一周目撞上过：cpu-tests 的 PASS/FAIL 是假的，交互退出码为 0 导致测试报 FAILED 而结果表仍打 PASS。

> **一张全绿的表，只有在框架确实报得出错的前提下才有意义。**

任何时候搭了一套自动判定，都要先放一个应当 FAIL 的用例进去，证明它能红；只跑正向用例，永远发现不了"框架根本报不出错"。

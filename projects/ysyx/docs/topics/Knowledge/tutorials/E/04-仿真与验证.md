## 1 仿真器：它是什么，Verilator 是哪一种

### 1.1 仿真的对象与功能验证的定义

RTL 代码描述的是**电路结构**（哪些元件、怎么连线）。仿真器拿这段代码做的事：用程序算出"这堆电路在给定输入序列下，每根信号线随时间变化的值序列"。功能验证就是拿这个值序列和预期对照。注意验证的是行为对不对，不是电路好不好（那是电路评估的事）。

### 1.2 两种范式：事件驱动与编译式

"仿真器"是一类工具，不是一款。按实现方式分两种范式，机制、速度、语义都不同：

| 范式 | 工作方式 | 代表 | 语义 | 速度 |
| --- | --- | --- | --- | --- |
| 事件驱动 | 解释执行：维护事件调度队列，信号变化才重算受影响的进程（IEEE 1364 标准的事件队列模型） | Icarus Verilog（iverilog）；商业三家内核也含事件驱动成分 | 全语义（四态 0/1/x/z） | 慢 |
| 编译式 | 把 RTL 整体翻译成 C++/SystemC 源码，再用本地编译器编成机器码执行 | Verilator；商业仿真器的高性能模式 | 可综合子集为主（两态 0/1） | 极快 |

商业谱系（Synopsys VCS、Cadence Xcelium、Siemens Questa）闭源收费，没有许可证就摸不到；但范式层面的理解是通用的。对照实验安排在批 2：同一个双控开关，iverilog 和 Verilator 各跑一遍，体感差异。两种范式的完整对照与工具谱系见 [00-仿真器的两种范式与工具谱系](../../fundamentals/00-仿真器的两种范式与工具谱系.md)，用到再读。

### 1.3 Verilator 的精确身份

"Verilator 用 C 语言模拟"是外行说法。精确说：**Verilator 是一个编译器 + 模型库**。它把你的 Verilog 读进来，优化后**生成**一堆 C++ 类源码（电路模型），再调用 g++ 把模型和你的 testbench 一起编成可执行文件；跑仿真就是跑这个可执行文件。所以仿真速度是机器码速度。编译流水各阶段在批 2 结合 make sim 逐阶段指认，细节篇 [01-Verilator的编译流水](../../fundamentals/01-Verilator的编译流水.md)。

两个我们必须知道的特性：

1. 两态语义：模型里只有 0 和 1，没有 x/z。未初始化信号怎么取值由 `--x-initial` 控制（批 3 lint 时展开，这正是和 UVM 线批 3 实测过的"x 传染"现象的接点）
2. 只认可综合子集加部分仿真语句：initial/$display/$finish 支持；延迟语句 #5 这类不可综合描述不支持——这正是它快的代价，也是"验证可综合 RTL"的定位

### 1.6 实验（批 1 实做）：双控开关

这是第一个"真正的电路模块"。vsrc 里的 Verilog（讲义原文）：

```verilog
module top(
  input  a,
  input  b,
  output f
);
  assign f = a ^ b;
endmodule
```

逐行讲：

- `module top(...); ... endmodule`：定义一个电路元件，名字 top，括号里是它的引脚（端口）
- `input a` / `input b`：两根输入引脚，各 1 位
- `output f`：一根输出引脚
- `assign f = a ^ b;`：数据流建模——一条连续的连线规则：f 的值永远等于 a 异或 b。这是组合逻辑（输出只由当前输入决定，不需要时钟）

行为上它是双控开关：两个开关状态相同灯灭，相异灯亮（异或真值表）。

csrc/main.cpp 里的 testbench。讲义给的是伪代码，展开成真代码（逐行讲）：

```cpp
#include <stdio.h>      // printf
#include <stdlib.h>     // rand
#include <assert.h>     // assert
#include "verilated.h"  // Verilator 运行时入口
#include "Vtop.h"       // Verilator 从 top 模块生成的类：V + 顶层模块名

int main(int argc, char** argv) {
  Verilated::commandArgs(argc, argv);  // 把命令行参数交给运行时（+verilator+ 开关将来用）
  Vtop* top = new Vtop;                // 造一个电路模型对象；端口就是这个对象的成员
  for (int i = 0; i < 100; i++) {      // 讲义版没有结束条件（Ctrl+C 退出）；我们加 100 次上限
    int a = rand() & 1;                // rand() 返回大整数，&1 截最低位，得 0/1
    int b = rand() & 1;
    top->a = a;                        // 驱动输入端口 a
    top->b = b;                        // 驱动输入端口 b
    top->eval();                       // 求值：组合逻辑传播到稳定，此刻 top->f 就是新输入下的输出
    printf("a = %d, b = %d, f = %d\n", a, b, top->f);
    assert(top->f == (a ^ b));         // 自动判错：不等即停并报出本行
  }
  top->final();                        // 收尾：释放运行时资源，放循环外
  delete top;
  return 0;
}
```

类语法的细节（`->` 访问、new/delete、成员）在 [03-C++类的基本用法](../../fundamentals/03-C++类的基本用法.md)，讲义原话"你只需要了解一些类的基本使用方法"。

两个机制必须当场想通：

1. `eval()` 干了什么：让模型把组合逻辑从当前输入推到稳定输出。一次调用即可，因为组合逻辑没有存储，传播有限步必收敛。
2. 为什么这个循环不需要时钟：`assign` 是纯组合，输出只跟当前输入有关，没有"什么时候采样"的问题。这是批 1 自测题（见篇末必答题表）。

判据（机器说了算）：

1. 100 次循环 assert 全绿，退出码 0
2. 注错见红：把 assert 条件故意改成恒假（如 `assert(top->f == 2)`），必须报错并指到该行——证明这套检查真的能报错（呼应 Bugs/README 铁律）；改回后恢复全绿

## 2 波形与一键仿真

### 2.1 波形的本质

波形 = 信号值随**离散仿真时间**变化的记录。Verilator 按时间步进推进仿真，每步可以记录"哪些信号的值变了"，攒下来就是波形文件。调试时它回答"这一拍谁变了、因果关系对不对"，是 RTL 调试的常用手段。

两种格式：

| 格式 | 形态 | 体积 | 支持者 |
| --- | --- | --- | --- |
| VCD（Value Change Dump） | 文本，IEEE 1364 标准定义 | 大 | 通用 |
| FST（Fast Signal Trace） | 二进制压缩 | 约为 VCD 的 1/50（讲义经验值） | 只有 GTKWave |

讲义推荐 FST：体积差 50 倍，代价只是换查看工具。生成 FST 的编译选项与运行时代码三步在 [05-波形格式与GTKWave](../../fundamentals/05-波形格式与GTKWave.md)（用到再读，批 2 实做）。

纪律（讲义警告 + 我们的落地）：波形文件大，长时间无限生成会耗尽磁盘。我们的规矩：波形只写 `/tmp`（沙箱临时层，不在 workbench 仓内）——顺带避开一个真坑：tracer 的 git_commit 会 `git add . -A`，波形落进 npc 目录会被收进 tracer 提交。

### 2.2 Makefile：make sim 一键仿真

反复敲长命令不可维护，写进 Makefile。npc/Makefile 现状（逐行讲）：

```makefile
all:
	@echo "Write this Makefile by your self."

sim:
	$(call git_commit, "sim RTL") # DO NOT REMOVE THIS LINE!!!
	@echo "Write this Makefile by your self."

include ../Makefile
```

- `sim:` 一个规则目标；批 2 把真命令写进它下面
- `$(call git_commit, "sim RTL")`：调用根 Makefile 里定义的 git_commit 多行宏——这就是 tracer-ysyx 原创性追踪：提交时切到 tracer 分支、`git add . -A`、记一条 "sim RTL"，再切回工作分支。**这一行不许动**（讲义红线 + 我们的 spec §六红线 1），动了开发追踪记录就断
- `@` 前缀：不回显命令本身
- `include ../Makefile`：把 workbench 根 Makefile 并进来，git_commit 宏和 STUID/STUNAME 都在那边

写 sim 规则就是把 1.7 的手动命令搬进来。Makefile 语法（变量、自动变量、call）速查见 [04-Makefile语法速查](../../fundamentals/04-Makefile语法速查.md)。

判据（批 2 实做）：`make sim` 一条命令完成编译加运行；运行后 `git log tracer-ysyx` 能看到 sim RTL 记录——这一步必须确认，讲义原话"你也需要确认 git 是否已经正确追踪了仿真的记录"。

### 2.3 结合 make sim 看 Verilator 编译流水

`make sim` 一次会经历：读入解析 Verilog → 展开（参数化模块按实例化生成）→ 静态优化 → 生成 C++ 模型源码 → 调 g++ 编译链接。批 2 实做时对着产物目录逐阶段指认，[01-Verilator的编译流水](../../fundamentals/01-Verilator的编译流水.md) 有各阶段说明与产物清单。这也是批 8 的伏笔：DiffTest 要通过模型对象访问 CPU 内部寄存器，得先知道模型长什么样。

## 3 NVBoard 与时序逻辑

### 3.1 NVBoard 是什么

NVBoard（NJU Virtual Board）是南京大学的教学项目：虚拟 FPGA 板卡，SDL 画界面，支持拨码开关、LED、数码管、UART、键盘、VGA。定位讲义说得直白：速度要求不高的场景下完全替代真板子。我们已在批 0 验证过它可编译（nvboard 顶层无 Makefile，它是"库"：工程经 include `scripts/nvboard.mk` 接入，编译它的自带 example 通过，32.6s，2026-11-12 实测）。

接入它的三件套（谁和谁建立联系）：

1. RTL 顶层：端口名对应电路的输入输出
2. 约束文件（.nxdc）：声明"端口名 ↔ 板卡上哪个元件的哪个引脚"
3. Makefile：include nvboard.mk，把板卡库和你的仿真链起来

讲义要求的读法："从 make 命令开始读代码"——先看 example/Makefile 怎么串起 nvboard.mk、auto_pin_bind.py（把 .nxdc 编译成 C++ 引脚绑定代码）、verilator 命令，再看示例 Verilog 顶层端口怎么被约束文件点名。批 3 实做，这也是前期研究 R-01 的完成动作。

### 3.2 时序逻辑：流水灯

有了时钟的电路是时序逻辑：输出不只看当前输入，还看电路里存了什么（触发器）。讲义给流水灯参考实现（先照讲义原文给 always 版，批 4 按模板重构——这个顺序差异是讲义自己的编排，不是我们偷懒）：

```verilog
module light(
  input clk,
  input rst,
  output reg [15:0] led
);
  reg [31:0] count;
  always @(posedge clk) begin
    if (rst) begin led <= 1; count <= 0; end
    else begin
      if (count == 0) led <= {led[14:0], led[15]};
      count <= (count >= 5000000 ? 32'b0 : count + 1);
    end
  end
endmodule
```

逐行讲：

- `output reg [15:0] led`：16 位输出，reg 类型（能在 always 里被赋值的变量类型；注意 reg 不等于"寄存器"，它只是 Verilog 的变量类型名）
- `reg [31:0] count`：分频计数器
- `always @(posedge clk)`：时序语义——只在 clk 上升沿这一事件发生时执行块内语句
- `led <= 1; count <= 0;`：复位分支，非阻塞赋值 `<=`（同一拍内所有赋值同时生效）
- `led <= {led[14:0], led[15]}`：拼接左移一位，最高位绕回最低位——这就是"灯依次流动"
- `count <= (count >= 5000000 ? 32'b0 : count + 1)`：数到 5000000 归零，等于把时钟分频，肉眼才能看见灯动

testbench 侧要造时钟和复位。讲义的两个原语（伪代码，逐行讲）：

```cpp
void single_cycle() {     // 推进一个时钟周期
  top->clk = 0; top->eval();  // 先置低
  top->clk = 1; top->eval();  // 再置高：0 -> 1 的变化就是"上升沿"
}
void reset(int n) {       // 复位 n 个周期
  top->rst = 1;
  while (n -- > 0) single_cycle();
  top->rst = 0;
}
```

两个必须当场想通的点：

1. 仿真器里没有真的"边沿"。clk 只是模型对象上的一个成员变量；你把它从 0 改成 1 再调 eval，模型才检测到这个变化并更新触发器。上升沿是我们两次置值**造**出来的。
2. `reset(10)` 复位 10 拍：给电路足够的时间进入确定的初态（10 是惯例值，不是魔法数；关键是不复位直接跑，触发器初值不确定，行为无从谈起）。

判据（批 3 实做）：流水灯接上 NVBoard，LED 从右往左依次亮起熄灭（讲义原文判据）；双控开关接上后拨开关控制对应 LED。

### 3.3 静态代码检查（lint）

Verilator 兼职 lint：`--lint-only` 只检查不生成模型，`-Wall` 打开全部检查类别，警告即输出。读法：每条警告在手册 Errors and Warnings 章节有编号和成因说明，先查章节再改。

处置分级（讲义规矩）：

1. 代码逻辑相关的警告：改代码消除，不关
2. 纯风格类且确认不影响逻辑：可用 `-Wno-<MSG>` 关闭单个类别（讲义例：`-Wno-DECLFILENAME`——文件名与模块名不一致这类）

为什么"建议总是开"（讲义理由 + 我们的补充）：位宽类错误（WIDTH/WIDTHEXPAND/WIDTHTRUNC）在两态模型里不报运行错、只悄悄截断，是"调好几天"级 bug 的头号来源；lint 一秒报出来。两态语义下这些警告为什么更要紧，见 [00-仿真器的两种范式与工具谱系](../../fundamentals/00-仿真器的两种范式与工具谱系.md) 的两态四态节——它和你在 UVM 线实测过的 x/z 传染是同一件事的两面。

判据（批 3 实做）：`--lint-only -Wall` 对 vsrc 全部代码零警告；注错见红：故意留一根未驱动信号，UNDRIVEN 类警告必须出现。

## 4 代码风格与规范：描述电路思维

讲义这一节是三 条规范加一套思维框架，直接关系将来 SoC 集成（不规范代码会让集成出问题，讲义原话）。

### 4.1 三条规范

1. **没深入理解事件模型之前，不用行为建模。** 行为建模（always 里写过程式逻辑）是"看着电路图，转成事件队列的思考，再写成行为描述"，每一步都可能引入偏差。讲义引用南大数电讲义："强烈建议初学者不要使用行为建模方式设计电路"。三种典型病：心里没电路图硬写行为描述（把 Verilog 当 C 写，综合出延迟大面积大的烂电路）；理解有偏差写出非预期电路；数据竞争导致综合结果不可预期。
2. **坚持行为建模的话，不用 negedge。** posedge 和 negedge 混用让时序收敛困难，影响后端物理实现；用官方模板或 Chisel 则不涉及此问题。
3. **不用锁存器。** 锁存器电平敏感、不受时钟驱动，时序分析工具难以处理；行为建模里 if 没写全分支是产生锁存器的头号来源。

### 4.2 描述电路 = 实例化 + 连线

回归 HDL 的本分：你手里有电路图纸，描述它就是两件事——**实例化**（在板上放元件）和**连线**（把引脚接对）。数据流建模（assign）和结构化建模（实例化模块）直接体现这两件事；行为建模把简单的事复杂化。所以讲义的立场：初学者不写任何 always，官方给了两个模板替你覆盖触发器和选择器——[06-Reg与MuxKey模板逐行拆](../../fundamentals/06-Reg与MuxKey模板逐行拆.md)（批 4 逐行拆，用到再读）。

### 4.3 事件模型四问（批 4 书面作答）

讲义给的四问，回答不了的就不许用行为建模。批 4 逐题书面作答，答录本节（先占位，作答后回填）：

1. 在硬件描述语言中，"执行"的精确含义是什么？
2. 是谁在执行 Verilog 的语句？是电路、综合器，还是其它的？
3. if 的条件满足就不执行 else 后的语句，这里的"不执行"是什么意思？和描述电路有什么联系？
4. "并发执行"、"顺序执行"、"任何一个变量发生变化就立即执行"、"任何情况下都执行"，它们分别如何在设计出来的电路中体现？

### 4.4 Chisel 立场

讲义对 Chisel 的规范同构：`when`/`switch` 的语义近似行为建模，初学者不用，选择器用 `Mux1H` 等库函数。切换时机按方案 A（批 4 末切，见 [E4-仿真与验证](../../../Engineering/Todo/E4-仿真与验证.md) §四）。

## 5 常见坑

1. 波形写进 npc 目录：会被 tracer 的 `git add . -A` 收走，且大文件耗磁盘——只写 /tmp（见 2.1 的纪律）
2. `Vtop.h` 找不到：编译顺序问题，模型头文件在生成目录里，include 路径随 --Mdir 变——批 2 实跑时确认
3. 端口在 C++ 侧的类型：1 位端口是 CData（uint8_t 别名），不是 bool，也不是 int——位宽类警告常从这里来
4. 顶层模块名与类名：类名是 V 加顶层模块名，--top-module 指错名字直接编不过
5. 动 git_commit 行：红线，tracer 记录断了无法补（见 2.2）
6. NVBoard 跑不起来报 DISPLAY 错：GUI 程序必须走沙箱 -Gui 批次（批 0 实测：无 DISPLAY 时 `gtkwave --version` 都报 GTK 初始化错）
7. lint 警告"能跑就不管"：两态下位宽截断不报运行错，埋的是最难调的雷（见 3.3）

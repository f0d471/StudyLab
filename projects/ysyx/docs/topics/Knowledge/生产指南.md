# 生产指南：一章知识资产怎么做出来

本文写给生产知识资产的人，目前是 AI。体例规则在[知识库 README](README.md)，本文讲流程：一章从立项到定稿要做哪些事，每一步的判据是什么，交给审稿者的提示词怎么写，以及已经踩过的坑。

按本流程完成的第一套样板是教程 [E/04-仿真与验证/01-Verilator把电路变成程序](tutorials/E/04-仿真与验证/01-Verilator把电路变成程序.md) 与 [fundamentals/02-Verilator/03-Verilator模型与eval](fundamentals/02-Verilator/03-Verilator模型与eval.md)。写新章之前，先通读这两篇和它们在 labs/ 下的实验目录。

## 1. 角色

| 角色 | 由谁担任 | 做什么 | 不做什么 |
| --- | --- | --- | --- |
| 生产者 | AI | 实验、check.sh、写章节、按审稿意见修改、登记 | 不替学员做讲义作业，不改 ysyx-workbench |
| 审稿者 | 没有参与写作的 AI（新开的子代理或另一个会话） | 只凭章节、labs 与依据源核对，给出问题单 | 不看写作过程，不接受生产者的口头解释 |
| 学员 | 用户 | 学习检验；在 ysyx-workbench 里独立完成讲义任务 | 不负责资产的正确性 |

## 2. 一章的流程

每一步都有产出和判据。判据没过，不进下一步。

### 2.1 圈定范围

1. 读讲义对应小节（离线镜像 `docs/site/ysyx.oscc.cc/docs/2607/...`），逐条摘出讲义布置的任务与必答题。
2. 对照阶段 spec 第五节的批次判据，确定本章覆盖哪几条任务。
3. 按第 6 节判定学术诚信边界。本章内容属于讲义要求学员独立实现的部分时，示例换成别的电路或别的程序。
4. 写问题链草稿：从一个读者能亲眼看到的现象出发，每个问题由上一个问题的答案引出。

判据：每条讲义任务都在问题链里有落点，或者写明"本章不覆盖，归第 N 章"。

### 2.2 沙箱实验

1. 建目录 `labs/<阶段>/<部分>/<NN-章名>/`（fundamentals 用 `labs/fundamentals/<NN-主题>/<NN-篇名>/`，篇号全局递增）。源码在 Windows 侧编辑，UTF-8、LF。
2. 一切编译和运行经沙箱，跑法见第 4 节。
3. 记录环境：工具版本（如 `verilator --version`、`g++ --version`）、系统版本、日期。
4. 正文打算写的每个说法，都先观察一次：命令、输出、退出码。说法来自源码的，记下文件路径和行号。

判据：正文要写的每个事实，都对应一条实测或一处源码。

### 2.3 写 check.sh 与 mutate.sh

1. 按第 3 节第 1 至 10 条写 check.sh，跑到全绿。
2. 按第 3 节第 11 条写 mutate.sh。每种改坏要么由 check.sh 自己构建的注错核对，要么是 mutate.sh 里的一项。跑到全部 OK。

判据：check.sh `N PASS / 0 FAIL`；mutate.sh `N OK / 0 BAD`；每个实验的每条输出，在 check.sh 里都有对应核对，并且至少有一种实跑过的注错能让它变红。环境判据（版本、文件大小、信号编号、工具帮助文本）在实验目录里没有可改的源码，mutate.sh 改 check.sh 里的期望值让它变红（坑 24）；运行库头文件里的类型定义这类事实由第 1 节的版本判据兜底。

### 2.4 写章节

1. 体例照知识库 README 第 4、5 节。
2. 正文里的输出从 `build/` 下的文件或 check.sh 日志里原样复制，不凭记忆写，不改动空格和标点。
3. 正文贴出的源码与 labs 里的文件逐字一致。
4. 正文直接陈述事实；来源集中写在篇末依据表，讲义的错误或过时说法写在依据表后的勘误小节。
5. 章内零 apparatus：判据清单与注错说明不进章，全部活在 labs 的 check.sh 与 mutate.sh 里。

### 2.5 独立审稿

用第 5 节的提示词开一个新的审稿者。审稿者交回问题单，每条带位置、证据和建议改法。

### 2.6 修复与复跑

1. 问题单逐条处理：修改，或者给出证据反驳。反驳的理由写进阶段 spec 第九节当天的日志。
2. 复跑 check.sh 与 mutate.sh，做第 7 节的风格检查。
3. 修改涉及事实或判据的，改完再审一轮。

### 2.7 登记

与章节放在同一次提交里。

1. tutorials/README 或 fundamentals/README 的篇目表：状态写"定稿 YYYY-MM-DD"。
2. 项目 README 当前进度节：哪章资产已定稿，check.sh 与 mutate.sh 的基线是多少（基线只登记在这里，章首元信息不写基线）。
3. 阶段 spec 第九节：追加一条日志。

### 2.8 学习检验

学员做，生产者只出题和记录，见第 8 节。

## 3. check.sh 规范

1. **位置**：放在实验目录里，文件名固定为 `check.sh`，开头注释写明它核对的是哪一篇。
2. **从零构建**：开头 `rm -rf build && mkdir -p build`，一切产物只进 `build/`。旧产物会冒充新结果，所以不允许跳过清空。
3. **分节**：`=== 第 N 节 <标题> ===`，N 与正文小节号一致，读者能从一条 FAIL 直接找到正文位置。
4. **一条判据一行**：打印 `PASS` 或 `FAIL` 加一句结论，结论写成读者能看懂的句子，例如"注错 2（删掉 eval）：f 永远是 0，assert 失败，退出码 134"。
5. **精确值与下限**：确定的输出（版本号、生成代码、没播种的 `rand()` 序列、退出码）用精确值判据；本机性能数字（1 秒写出多少行）用下限判据，同时打印实得值。
6. **版本判据放第 1 节**：版本不对时，后面的精确值判据都失去意义，先在这里亮红。
7. **注错**：check.sh 自己构建改坏的副本，用 `sed` 把源码改坏后写进 `build/mN/`，确认测试报错。常用的四类注错是改电路逻辑、删掉关键调用（如 `eval`）、触发 lint（如改文件名）、删掉程序自带的检查后用独立判据去抓。
8. **独立判据**：不依赖被测程序自己的 `assert`，用 `awk` 之类的工具从输出逐行重算。
9. **结尾**：打印 `N PASS / N FAIL / N SKIP`，脚本退出码为 0 当且仅当 FAIL 为 0。
10. **沙箱外直接退出**：开头检查工具在不在（`command -v verilator`），不在就说明原因并退出。
11. **mutate.sh**：与 check.sh 放在同一目录，核对正文"注错见红"的说法。每一项把实验文件复制到 `build/mut/<项名>/`，用 `sed` 改坏一处，跑副本的 check.sh，取出全部 FAIL 行，与正文写的变红判据比较：集合完全相同记 OK，多了或少了记 BAD 并打印差异；`sed` 没有改动文件也记 BAD。第一项"原样"不改任何文件，作对照，必须 0 条变红。判据名从 check.sh 的 FAIL 输出里复制，差一个空格也会记 BAD。末尾打印 `N OK / N BAD`，BAD 为 0 时退出码为 0。两个样板的 mutate.sh 可以直接照抄 `mut` 函数。

判据函数照样板抄：

```bash
PASS=0; FAIL=0; SKIP=0
ok()   { PASS=$((PASS+1)); printf '  PASS  %s\n' "$1"; }
no()   { FAIL=$((FAIL+1)); printf '  FAIL  %s\n' "$1"; [ -n "${2:-}" ] && printf '        %s\n' "$2"; }
skip() { SKIP=$((SKIP+1)); printf '  SKIP  %s\n' "$1"; }
eq()   { if [ "$2" = "$3" ]; then ok "$1"; else no "$1" "期望 $3，实得 $2"; fi; }
has()  { if grep -qE -e "$3" <<< "$2"; then ok "$1"; else no "$1" "输出里找不到 $3"; fi; }
hasnt(){ if grep -qE -e "$3" <<< "$2"; then no "$1" "输出里不该有 $3"; else ok "$1"; fi; }
```

## 4. 沙箱

从 Workspace 根目录执行：

```powershell
& .\Tools\wsl-sandbox\sandbox.ps1 -Action Run -Project ysyx -Command @('bash', '-lc', "bash '/workspace/docs/topics/Knowledge/labs/<实验目录>/check.sh' > /workspace/cache/e4-scratch/last.log 2>&1")
```

1. 沙箱 Run 任务里 `/workspace` 就是 `projects/ysyx`；`cache/` 是被 Git 忽略的目录，日志放这里。
2. Run 返回的是一段 JSON，只带 stdout 的尾部。完整输出重定向到日志文件，再从 Windows 侧读 `projects/ysyx/cache/e4-scratch/last.log`。
3. 命令里的中文路径可以直接传，已实测。
4. 用 `bash -lc` 启动登录 shell，`verilator` 才在 PATH 里。
5. check.sh 与 mutate.sh 共用 `build/`（check.sh 开头会清空它），一次只跑一个。
6. mutate.sh 每一项都完整跑一遍 check.sh，样板教程的 mutate.sh 本机约 15 分钟，fundamentals 03 的约 9 分钟，适合放后台。有的代理环境会拒绝命令行里带某些字样（实测是 `eval`，实验目录名里就有）的后台任务，这时把整条命令写进一个包装脚本，后台跑这个脚本。

## 5. 审稿

审稿者必须没有参与写作。提示词只给材料路径和检查项，不给生产者的结论，否则审稿者会顺着作者的说法核对。

```text
你是独立审稿者，没有参与这篇文章的写作。只依据下列材料判断，不接受作者的解释。

待审：<章节路径>
实验：<labs 目录>；check.sh 与 mutate.sh 最近一次的完整输出：<日志路径>
体例：Knowledge/README.md 第 4 至 9 节；流程与规范：Knowledge/生产指南.md
依据源：<讲义离线页路径>、<手册文本或 man 页路径>、<标准文本路径>、实验目录 build/ 下的生成代码

逐项检查。每个问题写四样：位置（小节号与原句）、问题、证据（文件:行号或命令输出）、建议改法。
1. 事实：每个事实性说法能否追到依据表里的一条依据；数字、输出、退出码是否与 check.sh 日志或 build/ 下的文件逐字一致。
2. 跳步：按 README 4.3，找出前提没讲就用、推导缺步、术语第一次出现没有解释的地方。
3. 章内零 apparatus：按 README 第 7 节，章内不应出现判据清单、[判] 块、注错说明、基线行，发现即报；正文与证据表引用的工件路径、实测数字，能否在 labs 的日志与 build/ 工件里逐字对上。
4. 讲义覆盖：讲义任务与必答题是否都有落点，对照篇末的讲义对照表。
5. 学术诚信：是否给出了讲义要求学员独立完成的实现。
6. 风格：emoji、`·`、破折号、"批 N"、正文里的"某某说"、先立误解再推翻的句式。

最后按严重程度排序：错误（事实错、判据假）在前，缺漏（跳步、未覆盖）其次，风格最后。某一项没有问题，写"未发现"。
```

## 6. 学术诚信边界

讲义要求独立完成的实现，本库不放答案。范围以讲义的学术诚信说明为准（离线页 `docs/site/ysyx.oscc.cc/slides/2607/01.html` 与 `docs/site/ysyx.oscc.cc/docs/2407/e/3.html`）。

1. E4 从"完成数字电路实验"起，到 sCPU、sEMU、DiffTest、NPC 的各项实现，教程只讲机制，示例换用别的电路或别的指令集片段。
2. 在此之前的环境搭建部分（Verilator 手册示例、双控开关、波形、NVBoard 接入），教程可以给完整示例；学员仍要在 ysyx-workbench 里自己写一遍。
3. AI 写的代码只放 labs/，不进 ysyx-workbench。

拿不准某段内容在不在边界内时，先问学员，不要先写。

## 7. 风格检查

定稿前对章节跑一遍，结果应为空：

```powershell
rg -n "——|·|批 ?[0-9]|原话|手册说|讲义说|不是.{0,30}而是|[\x{1F300}-\x{1FAFF}\x{2600}-\x{27BF}]" <章节路径>
```

再逐段对照去 AI 味的规则（`C:\Users\14297\.zcode\skills\lieflat-less-ai-tone\SKILL.md`）。教程里最常见的是这几种：先立误解再推翻；一个分句里用顿号串起三项以上；相邻几句同一个句法骨架；"核心是："这类提示语后接冒号；只为宣布列表而存在、以冒号结尾的句子；小标题用"一、二、三"通篇编号；非首段以"值得注意的是"开头却没有回指上文的词。

## 8. 学习检验

资产定稿不等于学会。每章定稿后，学员做三类检验，生产者出题并记录。

1. **预测**：读一节之前，先看这一节的命令，写下预测的输出和退出码；读完对照，预测错的项要能说出为什么错。
2. **闭卷讲解**：合上文档，把一节的问题链讲一遍，每个问题说出答案和证据在哪里。讲不下去的地方就是没学会，回去重读那一节。
3. **找错**：生产者依据 labs 里的注错项出题，给一段改坏的代码或一句错误的说法；学员指出错在哪里，并用一条命令验证。

记录写进阶段 spec 第九节，格式见该节。三类都过，项目 README 当前进度节登记"学习检验通过"与日期。之后学员在 ysyx-workbench 里独立完成讲义任务，按讲义的判据验收。

## 9. 已经踩过的坑

**坑 1：把资料综述当讲解。** 旧草稿正文里大段写"某书原话""手册里说"，读者读到的是谁说了什么，机制本身没有讲出来。做法：正文直接陈述机制，来源一律进篇末依据表。

**坑 2：用行数衡量质量。** 给单篇定行数下限，结果是同一件事换个说法再写一遍。做法：不设行数；每句话要么在描述现象，要么在推理，要么在解释原因。

**坑 3：先写正文，后做实验。** 旧版 E4 教程与 fundamentals 01 在实验之前写成，里面有"实测回填"的占位。实测以后发现五处问题。

1. 旧稿说 Verilator 不支持 `#5` 这类延迟语句；5.052 加 `--timing` 就能编译并按延迟推进时间。
2. 旧稿把"事件驱动"等同于"解释执行"；这是两个维度，VCS 就是编译式的事件驱动仿真器。
3. 旧稿说 Verilator 有"周期化倾向"；Verilator 5 的 `eval` 按 IEEE 1800 的调度区组织，生成代码里能逐区指认。
4. 旧稿说组合逻辑没有存储、传播有限步必收敛；组合环在 `eval` 里不收敛，报 DIDNOTCONVERGE。
5. 旧稿照搬了一条 testbench 守则（连续赋值只用于驱动 inout 引脚，组合逻辑用顺序代码写），并称它与讲义规范"同一个根"；讲义恰好要求初学者用 `assign` 和模板，不写 always。

做法：实验和 check.sh 先行，正文只写实测过的东西。

**坑 4：在线手册比安装版本新。** Verilator 在线指南是 5.054，沙箱里装的是 5.052，在线页面没有按版本区分的路径。做法：以安装版的 man 页（`tools/verilator-5.052/share/man/man1/verilator.1`）与实测为准，章首元信息写明版本。

**坑 5：abort 不刷 stdout 的缓冲。** `assert` 失败时，重定向到文件的 `printf` 输出全部丢失（实测 0 行）；在终端里能看到，是因为终端下 stdout 按行缓冲。做法：判据不依赖 abort 之前写进文件的 stdout；需要现场信息时打印到 stderr，或先 `fflush`。Verilator 自己的致命错误（如 DIDNOTCONVERGE）走 `vl_fatal`：调试级别为 0 时调用 `exit(1)`，`exit` 会先把缓冲写出去，`%Error` 行能进文件；加 `+verilator+debug` 运行时改调 `abort()`，又回到这个坑。

**坑 6：timeout 返回的是它自己的退出码。** 程序被 `timeout -s INT 1` 打断时，`timeout` 返回 124；加 `--preserve-status` 才返回程序自己的 130（128 加上 SIGINT 的编号 2）。沙箱里的 `timeout` 是 uutils coreutils 0.8.0，不是 GNU 版本，这两个退出码是在它上面实测的。

**坑 7：`-Wall` 让风格警告变成致命错误。** 文件名与模块名不一致会触发 DECLFILENAME。这条警告默认关闭，`-Wall` 把它打开，Verilator 的警告默认致命，构建直接失败。UNOPTFLAT 不同，它默认就打开，不加 `-Wall` 也会让构建失败。类名的规则是：给了 `--top` 用它，否则跟着第一个文件名走；不加 `-Wall` 时，`--top top` 能让类名和模块名一致，加了 `-Wall` 仍然报 DECLFILENAME。做法：labs 里文件名与模块名保持一致；需要演示时把它当成一种注错。

**坑 8：生成代码的空白随版本变化。** 用 grep 检查生成的 C++ 之前，先 `tr -d ' \n'` 去掉空白，判据只抓语义部分。

**坑 9：本机数字写成了精确值。** 无限循环 1 秒写出的行数每次不同，多次实测在 474 万到 573 万之间。做法：用下限判据并打印实得值，正文写明这是本机数字。

**坑 10：`rand()` 不播种恰好可以复现。** 不调用 `srand` 时，10 次输入的序列每次相同，正好当精确判据用。把它改成 `srand(time(0))`，就要同时改掉依赖这个序列的判据。

**坑 11：旧产物冒充新结果。** E4 环境四查时，NVBoard 示例第一次"编译成功"，其实是 make 发现无事可做，可执行文件是之前留下的。做法：check.sh 开头清空 `build/`；要证明"能编译"时先 clean。

**坑 12：标准文本抽取会印错条款号。** 从 PDF 抽出的 IEEE 1800-2017 文本把 4.4.1、4.4.2 印成了 3.4.1、3.4.2。做法：引用条款号之前，对照 PDF 页面确认。

**坑 13：运行时检查只在调试构建里。** 给 1 位端口写 2，普通构建不报错，f 被算成 2；加 `--runtime-debug` 构建才会当场拦下。做法：正文写"Verilator 会检查"之前，先确认说的是哪一种构建。

**坑 14：缓存构建与不用缓存的构建差很多。** 同一次 check.sh 里，手册示例用 ccache 时 bld 是 0.807 秒，设置 `CCACHE_DISABLE=1` 时是 5.115 秒。做法：写耗时就写明是哪一种；要比较时两种都在 check.sh 里构建，判倍数关系，并打印实得值。

**坑 15：新文件类型被 .gitignore 挡住。** 平台仓默认忽略 docs 下没有放行的内容。labs 下的 `.v` `.sv` `.c` `.cpp` `.h` `.sh` `Makefile` 与 `fig/` 下的 `.svg` 已放行，`build/` 被忽略。做法：新增别的类型先改 .gitignore，再用 `git status` 确认。

**坑 16：grep 判据匹配到了命令行。** 构建日志里会出现完整的命令行，命令里带 `-Wno-DECLFILENAME` 时，grep `DECLFILENAME` 在构建成功的日志里也能找到。做法：判据匹配诊断行本身的格式，例如 `%Warning-DECLFILENAME:`、`%Error-UNOPTFLAT:`，不只匹配关键字。

**坑 17：注错说明凭推理写。** 样板教程初稿各节的"改坏哪里、哪几条判据变红"是推出来的。mutate.sh 实跑以后，第 4 至 8 节有五处要按实测重写，实际变红的判据和写的不是同一组。做法：每条注错说明都由 mutate.sh 或 check.sh 的注错实跑核对，基线写进章首元信息。

**坑 18：从生成代码推执行次数，漏看了内部触发位。** 样板教程初稿推出"输入没变时 ico 区只调用一次"。fundamentals 03 用 `--runtime-debug` 构建、加 `+verilator+debug` 运行，打出逐行轨迹，才看到双控开关每次 `eval` 里 ico 区调用两次："本轮第一次调用"的内部位让第一次调用总是返回真。次数还随设计而变：fundamentals 03 第 7 节的时序电路在 ico 区没有要算的东西，`eval_ico` 无条件返回假，每次 `eval` 只调用一次。做法：从源码推出来的执行顺序和次数，用运行库的调试轨迹核对一遍，并写明是哪个设计。

**坑 19：推第一次 `eval` 时漏掉了初始化。** 样板教程初稿写"P2 那次 `a` 从 0 变成 1，所以触发"。实际上第一次 `eval` 先执行 `eval_static`，它把此刻的输入记成"上次的值"，随后 Settle 区已经把 `f` 算了一遍；ico 区第一次调用时比较结果是"没变"，触发位是被 `__VicoDidInit` 那段代码强制置 1 的。做法：推第一次 `eval` 时，把 `evalStatic`、`evalInitial` 和 Settle 区都算进去（`verilated.cpp` 第 4066 至 4079 行）。

**坑 20：`--no-timing` 下不加 `-Wall` 也会构建失败。** 设计里有 `#5` 这类延迟时，`--no-timing` 让 Verilator 报 STMTDLY。这条警告默认打开，警告又默认致命，所以不加 `-Wall` 也失败。初稿以为只有 `-Wall` 才会这样。做法：对比"带不带某个选项"时，每种组合都在 check.sh 里实跑一次；要让构建通过，单独加 `-Wno-STMTDLY`，或者加 `-Wno-fatal`。

**坑 21：只写了调试构建的一个选项。** 初稿说 `--runtime-debug` 让编译命令多了 `-DVL_DEBUG`。构建日志里实际多的是 `-ggdb -fsanitize=address,undefined -D_GLIBCXX_DEBUG -DVL_DEBUG=1`，链接命令也多了 `-fsanitize=address,undefined`。做法：选项的效果照构建日志原样写，check.sh 逐项核对。

**坑 22：工具帮助文本的空白和 GNU 版本不同。** 沙箱里 uutils 的 `timeout --help` 写的是 `124  if COMMAND times out`，124 后面是两个空格，按一个空格写的判据会失败。做法：匹配帮助文本时空白写成 ` +`，并把帮助文本存进 `build/` 供正文引用。

**坑 23：把讲义的提示框当成了必答题。** 讲义离线页用颜色区分框：`c-yellow` 是要做的任务，`c-green` 是提示，`c-red` 和 `c-blue` 是提醒与背景故事。初稿把绿色提示框"上述代码是什么意思?"写成了必答题。做法：讲义对照表照离线页的框类型和标题逐条列，正文里提到讲义时说清是哪一种框。

**坑 24：环境判据没法在实验源码上注错。** 版本号、文件大小、信号编号、工具帮助文本，实验目录里没有能改坏的源码。做法：mutate.sh 改 check.sh 里的期望值（例如把 ABRT 改成 KILL），确认这一条能变红；改期望值的做法登记在 labs。

**坑 25：把名字相近的函数当成同一种形态。** 初稿把 `eval_postponed` 和 `eval_act` 等并列写成"返回假、循环转一圈退出"。审稿核对运行库才发现：`eval_act` 到 `eval_react` 在各自的 do-while 里按返回值循环，`eval_postponed` 是 `void` 函数，不在任何循环里，由运行库在末尾直接调用一次（`verilated.cpp` 第 4129、4130 行）。写到"循环""返回值"这类机制时，逐个函数看定义，不从前一个函数类推。

**坑 26：把"一种可行做法"写成了"唯一做法"。** 初稿写"只加 `--no-timing` 构建不出来，还要关掉这条警告"，审稿指出加 `-Wno-fatal` 让警告不致命也能构建。写"必须""还要""唯一"之前，把替代选项至少想一遍。

**坑 27：把范围说法写得比实跑证据大。** 初稿写"check.sh 把四段区名抽出来核对"，实际 check.sh 只核对前三段；写"33 至 63 位的端口调试构建都查不出越界"，实际只实测过 33 位这一个。正文的说法按实跑范围收窄，或者把实验补上。

**坑 28：事实性判据不一定都要注错。** 生成代码、构建产物、轨迹行数这类判据，改一处源码就连带一大片变红，挑不出"只变红这一条"的注错；运行库头文件的类型定义在实验目录里没有可改坏的源码。做法与坑 24 一致：正文第 9 节如实列出哪些判据没有注错、靠版本判据兜底，不为了凑数硬加注错。

**坑 29：改坏参与计时判据的源码，会顺带打红计时判据。** 教程 check.sh 用"bld 时间是否超过 2 倍"核对 ccache 的效果。mutate.sh 里改坏 our.v 的那一项，让 ccache 里没有这份新源码的编译结果，第一次构建拿不到加速，ccache 判据跟着变红；而第二次跑同一项时缓存已经热了，又不变红。同一个改法两次跑结果不同，mutate.sh 的判据集合必须确定，所以这类判据用坑 24 的办法改期望值来覆盖，不在 our.v 上注错。

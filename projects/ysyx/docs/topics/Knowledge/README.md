# Knowledge：知识库

这里是 YSYX 二周目的知识资产：主线教程、前置基础与实验。它写给所有读者，包括以后复习的自己、
同样在学这门课的人、接手写后续章节的 AI。资产的价值在于能反复用：一篇定稿以后，任何人照着它
在沙箱里重跑，得到同样的输出，读懂同样的机制。

本目录的全部内容都是对事物本身的陈述。依据是沙箱实测、工具源码与生成代码、man 手册、标准文档；
来源集中列在每篇末尾的"依据"表里，正文不写"某某资料里说"。

## 1. 三部分

| 目录 | 收录范围 | 维护方式 |
| --- | --- | --- |
| [tutorials/](tutorials/) | 主线教程，按讲义阶段与部分组织（如 `E/04-仿真与验证/01-...md`） | 一章回答一串问题；一个部分一个目录，一章一个文件，与 labs 下的实验目录同名 |
| [fundamentals/](fundamentals/) | 前置知识与速查：一个名词或一个机制一篇讲透，成堆的选项、类型、函数表集中在这里 | 被教程引用才开篇；索引与状态见 fundamentals/README.md |
| [labs/](labs/) | 实验源码、check.sh 判据脚本、mutate.sh 注错自检、实验记录 | 目录与 tutorials/fundamentals 一一对应；check.sh 从源码重建一切再逐条核对，mutate.sh 核对正文的注错说明 |

三者的关系：教程回答"这件事为什么存在、怎么一步步做出来"；fundamentals 回答"这个名词到底是什么、
这类东西有哪些"；labs 回答"做没做对"，由机器判定。

生产这些资产的完整流程、质量关卡、提示词模板与已踩过的坑，写在[生产指南](生产指南.md)。
写新章节之前先读它。

## 2. 两条线：资产线与学习线

1. **资产线（AI 做）**：沙箱实验与 check.sh 先行，再写章节，再交给一个没参与写作的审稿者独立审，
   修完才算定稿。产出全部在本目录。
2. **学习线（学员做）**：读定稿章节，做预测、闭卷讲解、找错三类检验；然后在 ysyx-workbench 里
   独立完成讲义布置的任务。检验结果记在对应阶段 spec 的开发日志（E4 是
   [E4-仿真与验证.md](../Engineering/Todo/E4-仿真与验证.md) 第九节）。

资产定稿不等于学会。项目 README 的进度节把两条线分开写：哪章资产已定稿、哪章学习检验已通过。

**学术诚信边界。** 讲义要求独立完成的实现，本目录不放答案：从 E4 的数字电路实验起，到 sCPU、
sEMU、DiffTest、NPC 的各项实现，教程只讲机制，示例换用别的电路或别的指令集片段，不给可以直接
交上去的代码。AI 写的实验代码只放 labs/，不进 ysyx-workbench；学员工程里的每一行由学员自己写。

## 3. 写给谁

读者的起点按最低处算：会用 Linux 终端，写过 C（指针、结构体、`rand`、`assert`、退出码），
做过 HDLBits 程度的 Verilog，会读简单的 C++ 类（`new`/`delete`/`->`），会读简单的 Makefile。
C++、Makefile、GCC 的通用基础不在本库展开，用到时就地讲清本章需要的那一点。

读者的目标是能自己从零推出每一章的结论。由此定下总原则：**一次只加一块积木，
每一块都从上一块推出来。** 读到任何一句，都应该能说出"这句话是从前面哪句推过来的"；说不出，
就是写跳了。

## 4. 讲解的写法（tutorials 与 fundamentals 共用）

### 4.1 问题链

每一节从一个问题开始，这个问题由上一节的结论引出来。节首用一两句话接上线：

    上一节：改了 top->a，读到的 f 还是旧值。
    这一节的问题：是谁、在什么时候把 a ^ b 算出来的？

一节只回答一个问题。回答完，节末写"这一节搭好的积木"：现在多知道了什么，它马上引出哪个问题。
节首不甩总表、不堆名词，总表放在讲透之后。

### 4.2 一块新积木的五步

一个新概念第一次出现时按五步讲，不省略：

    1. 现象    先让读者看见它：一条命令、一段输出、一个报错
    2. 身份    它真实是什么：一个文件、一个 C++ 类、一段生成代码、一条约定
               按真实构造描述，比喻至多一句作辅助
    3. 必要性  没有它会怎样；从"如果没有"推出"所以必须有"
    4. 机制    它怎么工作，一步一步写，中间步骤不省
    5. 回扣    回到第 1 步的现象，用刚讲的机制把它完整解释一遍

### 4.3 不跳步

1. 推导里每一步都写出来，包括看起来显然的那一步。"显然""不难看出""记住即可"不出现在论证里。
2. 一个结论依赖的前提，必须在它之前讲过；没讲过的就地讲。
3. 数字算给读者看：`seen: 00=3` 是怎么数出来的，对着 10 行输出数一遍。
4. 引用前文写清是哪一节的什么结论，不只写"如前所述"。

### 4.4 就地讲透，深入再跳

正文出现的前置名词，先用几段话讲到"读者能顺着往下读"的程度；想彻底弄懂的，再给 fundamentals 链接。
不能只留一个链接让读者去别处补课再回来。

### 4.5 命令与输出：四步

    要回答的问题    这条命令是为了看清什么
    命令本身        完整给出；每个参数第一次出现时说明它在管什么
    真实输出        沙箱实跑的原样输出，标注日期与版本（章首元信息统一标注即可）
    逐行读          输出里看哪一行、哪一列，它说明了什么，和前面哪个数对得上

代码完整给出并逐行讲：声明、循环、赋值方向、标点的作用，第一次出现时都讲。能跑的代码放 labs/，
正文贴出的版本与 labs 里的文件逐字一致。

### 4.6 常见误解

容易想错的地方就地澄清，写成"容易以为 X；实测是 Y；原因是 Z"。

### 4.7 语言

1. 真实描述优先于比喻。先讲行为（输入什么、能观察到什么、失败时怎样），再给术语和内部原理。
2. 新术语先给中文含义、全称和具体对象，再讲机制（例：ico = input combinational，Verilator
   在每次 eval 里专门计算"只依赖顶层输入的组合逻辑"的那个区）。
3. 不用 emoji；不用 `·` 作分隔符，枚举用序号；不用破折号串句子。
4. 读者面向的文字里不出现内部工作代号（"批 N"），写"第 N 章"或具体小节。
5. 文字量不设上下限。描述、分析、解释都写出来；每句话要么在描述现象，要么在推理，要么在解释原因，
   不注水、不换个说法重复。

## 5. 教程的章结构（tutorials/）

    章首元信息      实验目录、check.sh 与 mutate.sh 基线、实测环境（日期、系统、工具版本）、对应讲义小节
    读前须知        需要的底子，每条一句"为什么需要"；可后读的 fundamentals 标明
    在整条链里的位置 上接哪章、下接哪章、补的是整个项目的哪一块
    不学它会怎样    读者后面会亲眼遇到的具体现象或报错
    0 起点          从一个现象出发，列出读完要能解释什么；不提前给答案
    1～N 正文       问题链，一节一个问题，节末"这一节搭好的积木"，每节或每两节一个 [判] 块
    回看            整章问题链串一遍：问题、答案、证据在哪一节
    自检            每题都能用命令验证，标出对应小节
    已知的坑        现象、原因、在哪一节
    交出了什么      现在能做到的、还做不到的、下一章
    依据            说法与来源对照表；讲义任务与本章小节的对照表

实验强度标在小节标题上：

    [做 L1] 复现    跑通并观察现象，建立事实基础
    [做 L2] 改造    给定目标改现有代码，必须改出预期的可观测变化
    [做 L3] 从零写  自己写一段完整的程序
    [判]            可逐条打勾的检查项，每条都能注错见红

L4（把能力落进 ysyx-workbench）是学员的事，教程里只写"讲义要你做什么、判据是什么"，不代做。

## 6. 依据与版本

1. 每个事实性说法都要能追到一条依据：沙箱实测（labs 里有对应 check 项）、生成代码或运行库源码
   （路径加行号）、man 页或手册章节、标准条款（如 IEEE 1800-2017 第 4.4 节）。
2. 依据集中在篇末"依据"表。正文直接陈述事实，不写"手册说""讲义说"。
3. 版本敏感的行为一律实测，并在元信息写明版本。在线手册（5.054）与安装版本（5.052）不一致时，
   以安装版本的 man 页与实测为准。
4. 讲义里的事实错误或过时说法，在"依据"表后的"勘误"小节写明：原文、实测、各自版本。

## 7. 实验、判据与数字

1. **判据跟着实验走。** 每个 [判] 块的每一条都要能"注错见红"：故意改坏一处，判据必须变红。
2. **check.sh 自带注错。** 除了"正确时全绿"，check.sh 还要构建改坏的副本，确认测试真能报错；
   必要时用不依赖被测程序的独立判据（例如用 awk 逐行重算 `a ^ b`）。
3. **注错说明要实跑。** 每个 [判] 块末尾写明改坏哪里、哪几条判据变红；同目录的 mutate.sh 把这些改坏逐个
   做在副本上，核对变红的判据与正文完全一致。
4. **数字必须实跑。** 输出、退出码、行数、耗时一律来自沙箱实跑并标注日期。环境不可用时沿用已归档的
   实测，不重编、不改数字。
5. **GUI 判据**（NVBoard、GTKWave）机器无法读屏时，以截图或学员当面确认为证，记录里写明是哪一种。
6. check.sh 末尾打印 `N PASS / N FAIL / N SKIP`，mutate.sh 末尾打印 `N OK / N BAD`；两个基线登记在项目 README 的进度节，
   判据变化的提交同步更新基线。

## 8. 配图

1. ASCII 图多用：数据流、调用链、对象布局、改动前后对照。放在代码块里；框线与对齐只用英文、数字和
   代码里的真实名字，中文标注写在框外（行尾或下方）；一张图不超过约 76 列；图后紧跟一段文字说明
   从哪里看起。
2. 复杂的过程做 SVG，放所在目录的 `fig/`，命名 `<篇号>-<名称>.svg`。白底，无渐变、阴影、装饰圆角；
   实线是会执行的通路，虚线是未接入的通路；颜色只承载一种语义且图内有图例；最小字号 9px；
   提交前用浏览器无头渲染一次，确认无重叠、无裁切。

## 9. 状态

每篇只有两种状态，标在 fundamentals/README 与 tutorials/README 的篇目表里：

1. **定稿**：按[生产指南](生产指南.md)走完全流程（实验、check.sh、mutate.sh、独立审稿、修复），标注定稿日期。
2. **素材稿**：旧流程产出，未经实验与审稿，可能含事实错误；篇首有提示框，只作重写素材，不作学习依据。

文档通用最低要求（术语、引用、实验记录格式）见[资料目录 README](../../README.md)第 4 节。
